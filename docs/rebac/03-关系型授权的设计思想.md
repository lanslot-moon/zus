# 03. 关系型授权的设计思想：为什么关系比角色更接近真实业务

## 权限系统真正要表达的到底是什么

如果把所有权限判断都翻译成人话，你会发现它们本质上都在回答某种关系问题：

- 这个人是不是这个对象的 owner
- 这个人是不是某个被授权组的成员
- 这个对象是不是挂在某个可见父对象下面
- 这个用户是不是因为上层组织关系而获得权限

注意，这些问题的共同点不是“角色”，而是**关系**。

角色当然有价值，但角色更像一种方便管理的抽象；而在复杂业务里，真正决定权限的往往是对象之间、对象与用户之间、组与用户之间的关系链。

## 为什么说 ReBAC 是“关系证明系统”

ReBAC 的精髓不在于“多了几个关系字段”，而在于它把授权判断变成了一种**证明过程**：

1. 模型先规定哪些关系可以传播
2. 事实层提供当前有哪些关系存在
3. 引擎尝试从请求主体出发，寻找一条满足模型规则的授权路径

如果存在这样一条路径，则授权成立；如果找不到，则不成立。

这种思维方式与传统“查某人有哪些角色”非常不同。  
它要求系统关注的不是单点身份，而是路径、集合和传播规则。

## ReBAC 里的几个关键语义单位

### Subject

被授权主体。  
通常是用户，但不一定局限于人，也可能是：

- 用户组
- 服务账号
- 组织中的某个 userset

### Object

被访问对象。  
可以是文档、目录、项目、组织、仓库、工单或任何业务实体。

### Relation

关系语义。  
它既可以表达“角色感很强”的语义，比如 `editor`、`owner`，也可以表达“结构关系”，比如 `parent`、`member`、`belongs_to`。

### Tuple

关系事实。  
用于说明某个 subject 与某个 object 当前存在某种 relation。

### Userset

不是单个用户，而是某个对象上的一组用户集合。  
例如：

- `group:eng#member`

它表示 engineering 这个 group 的所有 member。

### Tuple-to-userset

这是 ReBAC 表达传播能力的关键。  
它允许模型先通过一个 tuple 找到另一个对象，再在那个对象上继续求值。

例如：

- `viewer from parent_folder`

它的意思是：先拿到当前文档的 `parent_folder`，再看这个 folder 上谁是 `viewer`。

## 为什么关系比角色更贴近复杂业务

### 第一类问题：局部身份

“项目 A 的管理员”和“项目 B 的管理员”从岗位角度看像两个角色，但从业务语义看更像：

- `user` 与 `project:A` 存在 `admin`
- `user` 与 `project:B` 存在 `admin`

这时如果继续把它们做成全局角色，就容易角色爆炸；  
如果把它们做成关系，语义就会自然很多。

### 第二类问题：层级传播

真实系统里常见的不是平面资源，而是层级资源：

- organization -> project -> document
- folder -> subfolder -> file
- tenant -> workspace -> dashboard

如果上层对象的可见性可以传播到下层对象，那么关系建模会比角色建模自然得多。

### 第三类问题：群组和协作

协作系统里最常见的权限路径，通常类似这样：

- 这个组能访问某个项目
- 当前用户属于这个组
- 所以当前用户能访问项目下的某些对象

这是典型的“关系链推导”，而不是岗位型角色问题。

## 为什么 ReBAC 会天然适合协作系统

协作系统最难的地方，不是动作种类多，而是关系网络复杂。  
例如：

- 文档 owner
- 评论提及
- 群组共享
- 目录继承
- 外部访客
- 项目成员
- 组织管理员

这些语义都要求系统理解：

- 人与对象的关系
- 对象与对象的关系
- 关系如何沿路径传播

这正是 ReBAC 最擅长的部分。

## ReBAC 与图模型的关系

ReBAC 经常被描述为图授权模型，因为它天然可以被理解为图：

- 节点：用户、组、组织、资源
- 边：关系 tuple
- 推导：沿边和规则做传播

![ReBAC 授权路径传播图](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/03-rebac-path-propagation.svg)

需要注意的是，ReBAC 不等于“你必须用图库存储”。  
图只是它的语义理解方式。实际工程上，很多成功系统依然把事实存储在结构化关系存储中，然后在引擎里做图式求值。

## ReBAC 不是万能的

关系很重要，但不是一切。

### 它不适合直接表达所有上下文条件

例如：

- 今天是不是工作时间
- 当前设备是不是受信设备
- 当前请求 IP 是否命中白名单

这类问题本质上更适合放到条件系统，而不是硬写进关系图。

### 它不等于不再需要角色

角色仍然非常有价值，尤其是：

- 后台岗位
- 稳定组织职责
- 需要批量授权和复用的场景

只是角色应该成为一种建模形式，而不是把所有关系都压成角色。

### 它也不意味着系统更简单

ReBAC 的表达力更强，但工程复杂度也更高。  
它要求：

- 更清晰的模型边界
- 更统一的事实层
- 更成熟的求值引擎
- 更明确的一致性和缓存设计

## ReBAC 和 ABAC 的正确关系

很多人会把 ReBAC 和 ABAC 看成对立路线。  
其实更成熟的工程实践通常是：

- 用 ReBAC 负责关系语义和传播路径
- 用 ABAC 负责关系在上下文中的成立条件

因此，条件不是要替代关系，而是要附着在关系事实上，作为运行时增强层。

## ReBAC 的一句工程总结

如果你要把 ReBAC 的核心设计思想压缩成一句话，可以这么说：

**权限不是“某人属于哪个全局角色”，而是“在当前模型和当前事实下，能否证明主体与对象之间存在一条满足规则的授权路径”。**

这句话基本概括了 ReBAC 的世界观，也解释了为什么它会成为复杂协作系统的天然底座。

## 本文小结

你可以带走四条判断：

1. **ReBAC 的核心不是字段数量，而是证明思维。**
2. **关系传播比静态角色更适合表达复杂对象结构。**
3. **图是 ReBAC 的语义视角，不等于必须用图库落地。**
4. **ReBAC 最强的场景，是协作、多租户、层级资源和关系传播。**
