# 07. 一致性、数据同步与多节点最新视图

## 权限系统里最危险的“旧数据”长什么样

权限系统中的一致性问题，并不是一个抽象的数据库理论题。  
它会直接变成下面这些用户可感知的事故：

- 用户刚被撤权，却还能继续访问
- 用户刚被授权，却短时间内还看不到对象
- 页面列表和详情接口看到的状态不同
- 多个节点下同一个请求在不同实例上返回不同结论

这些问题的共同根源是：

- 写入已经发生
- 但读取并没有明确知道自己应该看到哪个时间点的数据

在安全敏感系统里，这不是“偶尔不一致”，而是实实在在的正确性问题。

## 为什么 Zanzibar 会把一致性放到系统中心

Zanzibar 的标题本身就强调了 `Consistent`。  
这不是修辞，而是承认了一件事：

**权限系统如果不能说明自己读的是哪个时点的数据，就无法稳定保证授权正确性。**

这类风险在业界通常会被称为 “New Enemy Problem”：

- 某用户刚被移出共享范围
- 但系统某些缓存或副本还没看到这次变更
- 于是旧权限被短暂错误保留

对于权限系统而言，这类“旧数据可访问”往往比普通读延迟问题更敏感。

把这个问题说得再具体一点：  
如果一个文件刚刚被撤销分享，用户在 3 秒内还能继续打开，这在普通业务里也许只是“延迟同步”；但在权限系统里，它已经是一次真实的越权窗口。  
也正因为如此，权限系统的一致性设计从来不是单纯的数据库优化题，而是安全边界设计题。

## 为什么多节点环境下一致性天然更难

只要系统引入下面任意一种机制，一致性就不再是单机问题：

- 多应用实例
- 只读副本
- 本地缓存
- 分布式缓存
- 异步日志或变更订阅

这意味着一次授权判断可能涉及：

- 当前节点的本地缓存
- 某个副本数据库
- 某个历史快照
- 某个尚未刷新完成的索引状态

如果系统没有明确的 consistency contract，调用方就会陷入“到底看到的是最新结果还是缓存结果”的不确定性。

## 为什么需要 zookie / revision / token

为了让读取操作知道“至少应该看到哪个时点之后的数据”，现代 ReBAC 系统通常会引入某种版本令牌：

- Zanzibar：`zookie`
- SpiceDB：`ZedToken`
- 其他系统：`revision`、`snapshot token`、`consistency token`

这些 token 的核心作用不是“做缓存 key”，而是：

- 描述一个可比较的时间点或快照边界
- 让读取操作可以声明对新鲜度的要求

这里最值得强调的是：  
token 解决的不是“全球绝对最新”问题，而是“请求应该以什么新鲜度下限读取”的问题。  
这两者差别很大。

- “全球绝对最新”意味着所有副本、缓存、日志、索引都已经同步完成
- “至少不早于某个 token”只要求结果不要回退到更旧状态

后者更现实，也更适合作为 API 契约。

## 这类 token 到底解决什么

可以把它理解成一个非常实际的约定：

- 写请求返回一个“我已经至少包含到这个时点”的标识
- 后续读请求可以带上它
- 读系统据此保证：
  - 至少和这个时点一样新
  - 或精确读取这个快照
  - 或明确选择“低延迟优先”

这就把“一致性”从隐性猜测变成了显性协议。

## 主流系统通常提供哪些一致性模式

不同系统命名不同，但大体上会落在几种模式里：

### 低延迟优先

尽量命中缓存、尽量快地返回结果。  
优点是快，缺点是更容易读取到相对旧的状态。

### 至少不早于某个 token

如果调用方带来某个 revision/token，系统保证结果至少不早于这个时间点。  
这是很多业务里最平衡的选择。

### 精确快照

读取指定快照。  
好处是适合分页和严格一致的多次查询，代价是快照可能过期，也更依赖底层存储能力。

### 完全一致

尽可能绕过缓存，读取最新视图。  
这通常代价最高，因此不适合作为所有请求的默认模式。

在工程上，一个比较成熟的做法通常不是“只有一种最强模式”，而是按业务请求分层：

- 列表首屏、探索式查询：允许低延迟优先
- 刚写后读：要求至少不早于写返回 token
- 审计、导出、分页遍历：要求固定快照
- 高风险操作前校验：要求更强一致

只有把一致性能力做成“分层能力”，授权系统才能同时兼顾正确性和成本。

## 为什么“完全一致”也不一定意味着“立刻看到所有新数据”

这是一个非常值得开发者注意的点。

很多人听到 fully consistent，直觉会认为：

- 这一定能保证刚写完马上在所有地方读到

但在真实分布式系统中，尤其是多节点数据库和分布式时钟环境下，这并不总是成立。  
例如 SpiceDB 官方文档就明确说明，在特定底层存储上，完全一致模式未必等于最强的 read-after-write 语义，推荐在需要时结合 token 使用。

这说明一致性不是一句“我开了强一致”就能自动解决，而是必须和：

- 存储实现
- 节点时钟
- 缓存设计
- API 语义

一起理解。

进一步说，在多区域、多副本、异步缓存失效的系统里，“最新”本身就是一个层级化概念：

- 存储最新
- 主节点可见最新
- 某个副本可见最新
- 某个缓存体系可见最新
- 某个列表索引可见最新

如果架构文档里不把这些层级说清楚，团队内部就会不断出现一种误解：  
“写成功了，为什么这里还看不到？”  
实际上大家讨论的根本不是同一个“最新”。

## 多节点系统下如何尽量读到“足够新”的数据

如果你的系统是自研 ReBAC 服务，最实用的设计通常是：

1. 写入返回 revision/token
2. 客户端或业务主库记录该 token
3. 后续关键读请求带上 token
4. 授权服务按 `at least as fresh` 语义执行

这样做的价值在于，它让“刚写完就要读到”的诉求变成了显式能力，而不是“赌缓存刚好刷新了”。

如果再往前一步看，多节点系统里往往还有三条隐藏路径也会影响一致性：

- 本地结果缓存
- 派生索引或投影表
- 搜索型接口的候选集缓存

这意味着“主事实层已经追平”并不自动等于“所有授权相关查询都追平”。  
因此成熟系统才会把：

- revision/token
- changelog/watch
- 缓存失效
- 列表快照

一起放进一致性设计里，而不是只盯数据库复制延迟。

## 一致性与列表查询为什么更难

`Check` 是单个判断。  
`ListObjects` 和 `ListUsers` 则经常涉及：

- 候选集枚举
- 分页
- 多次查询

如果这些查询没有统一绑定到某个 snapshot/token，就容易出现：

- 第一页和第二页结果不一致
- 列表和详情不一致

因此对列表型查询来说，快照语义通常比单次 `check` 更重要。

这是因为列表查询有两个额外复杂点：

### 第一，分页会跨越时间

如果第一页在 revision A，第二页在 revision B，那么：

- 某些对象可能在第二页前被插入
- 某些对象可能在第一页后被删除
- 用户最终看到的集合既不是 A 时刻的快照，也不是 B 时刻的快照

这类错误在权限列表里尤其敏感，因为它会直接破坏“用户到底能看到哪些对象”的认知。

### 第二，列表往往依赖候选集

很多 `ListObjects` 并不是“对所有对象做一遍 check”，而是先通过索引或反向查询拿到候选，再交给 evaluator 过滤。  
如果候选集和 evaluator 不共享同一快照边界，列表就很容易出现：

- 候选里有但最终不该看到
- 候选里没有但其实已经应该看到

所以列表接口不只是“check 的批量版”，它对快照和一致性的要求往往更高。

## Watch 与变更日志在一致性中的角色

除了请求级 token，现代系统还常配合：

- changelog
- watch stream
- 缓存失效事件

这些机制的作用不是直接代替一致性 token，而是：

- 帮助节点知道什么时候该失效缓存
- 帮助下游索引或投影尽快追上最新状态
- 帮助多节点服务维持较小的可见性滞后窗口

换句话说：

- **token 负责请求级一致性**
- **watch/changelog 负责系统级同步收敛**

更进一步说，watch 的真正价值不只是“我能订阅到变化”，而是它给了系统一个有序推进的位置概念。  
有了这个位置概念，很多外围能力才可能建设出来：

- 缓存消费者知道自己同步到了哪里
- 搜索投影知道自己追平到了哪里
- 审计系统知道哪些变更已经处理过
- 故障恢复后知道从哪里续读

因此 changelog/watch 在成熟架构里通常不只是附属接口，而是分布式收敛机制的一部分。

## 开源系统通常怎么处理这件事

OpenFGA 更强调以 API consistency mode 的方式，把调用方对新鲜度的需求显式表达出来。  
SpiceDB 则在 revision、watch、consistency 等概念上提供了更细粒度、更“权限数据库化”的表达。

二者路线虽然不同，但共同点非常明显：

- 一致性不能只靠缓存失效猜测
- 列表能力必须和 revision/snapshot 语义绑定
- 写后读需求必须有显式承载物
- 系统内部同步也需要自己的位置概念

这也是为什么现代授权系统越来越像一个“有一致性 contract 的分布式数据系统”，而不只是一个业务服务。

## 开发者最容易忽略的几个一致性问题

1. 把缓存命中率当成成功，而忽略是否命中的是旧结果
2. 用同一默认模式处理所有读请求
3. 忘了列表查询也需要 snapshot 语义
4. 写入成功后，没有任何 way 把“新鲜度要求”传递给后续读请求

## 本文小结

你可以带走五条判断：

1. **权限系统中的一致性，首先是正确性问题，不只是性能问题。**
2. **zookie / revision / token 的本质，是把“读多新”变成显式协议。**
3. **完全一致不是一句口号，它取决于底层存储、缓存和节点模型。**
4. **列表查询比单点 check 更需要快照语义。**
5. **watch/changelog 负责系统同步，token 负责请求级一致性，两者角色不同。**
