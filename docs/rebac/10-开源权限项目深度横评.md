# 10. 开源权限项目深度横评：OpenFGA、SpiceDB、Casbin、OPA

## 为什么这一篇不能只做“工具介绍”

很多文档写开源项目对比时，最终都退化成：

- OpenFGA 是什么
- SpiceDB 是什么
- Casbin 是什么
- OPA 是什么

这种介绍当然有价值，但对开发者做技术选型帮助不大。  
真正有价值的问题是：

- 它们分别解决哪一类权限复杂度
- 它们对事实层、模型层和执行层分别提供了多少现成能力
- 它们在一致性、高可用和 explain 上各自走了什么路线
- 哪些能力是系统自带的，哪些能力需要业务方自己补

这才是工程选型真正关心的问题。

## 先给一个总判断

从问题域上看，这几个项目并不完全处于同一层：

- **OpenFGA / SpiceDB**：更接近“完整 ReBAC/FGA 服务”
- **Casbin**：更接近“灵活授权库/嵌入式授权框架”
- **OPA**：更接近“通用策略引擎”

所以最重要的一个前提是：

**不要把它们误认为是功能完全等价的替代品。**

## 先看对比主轴

![开源项目能力矩阵](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/09-oss-capability-matrix.svg)

在进入逐项比较之前，先建立一个很关键的判断框架：  
这四类项目的根本差异，不是“功能多少”，而是它们分别把哪一层当作自己的核心产品。

- OpenFGA：把细粒度授权服务本身当产品
- SpiceDB：把 Zanzibar 风格权限数据库当产品
- Casbin：把授权执行框架当产品
- OPA：把通用策略决策引擎当产品

这决定了它们对同一个问题的默认回答完全不同。  
例如你问“列表查询是否应该是内建能力”，对 FGA 服务而言这是核心职责；对通用策略引擎而言，这更像外围集成问题。

## 一、模型能力

### OpenFGA

- 明确以 FGA/ReBAC 为核心
- 有 DSL、类型定义、关系定义、条件
- 模型边界和 tuple 语义都很清晰

### SpiceDB

- 同样是 Zanzibar-inspired
- schema 语言强、userset 和传播语义成熟
- caveat 机制完整

### Casbin

- 模型非常灵活
- 支持 ACL、RBAC、ABAC、ReBAC、PBAC 等多种模式
- 更像授权建模工具箱，而不是单一语义产品

### OPA

- 更关注策略表达与执行
- 不天然提供完整的 ReBAC 域语义
- 更适合做策略层、上下文决策层

这里最值得提醒的一点是：  
“模型能力强”不只意味着语法多，而意味着系统是否替你固定了问题域。  
OpenFGA 和 SpiceDB 的优势，恰恰在于它们愿意牺牲一部分泛化自由，换来：

- 更稳的关系语义
- 更统一的 API
- 更少的业务方自由发挥空间

而 Casbin、OPA 的自由度更高，也意味着业务方要自己承担更多建模一致性的责任。

## 二、关系存储方式

### OpenFGA

- 明确围绕 relationship tuples
- 模型与事实分层

### SpiceDB

- 关系事实和 schema 都是一等对象
- 重点强调 relation/permission/subject 的一致语义

### Casbin

- 更依赖 policy + matcher
- 可借助不同 adapter 落存储
- 关系事实与系统模型之间的结构边界不如 FGA 服务那样强制明确

### OPA

- 本身不是关系数据库
- 需要外部输入 structured data
- 关系事实如何组织，更多由接入方决定

这也是为什么一旦系统开始强调：

- tuple 作为唯一事实层
- 反向查询
- 快照一致性
- 多节点 watch

那么 OpenFGA / SpiceDB 通常会更自然。  
因为这些能力在它们那里不是“可选组合”，而是产品核心假设的一部分。

## 三、DSL / Schema 形式

### OpenFGA

- 有明确 DSL
- 强调 type、relation、condition 和 model version

### SpiceDB

- 有 schema 语言
- caveat 和 relation 约束表达能力较强

### Casbin

- 使用 model conf + policy
- 灵活，但可读性与系统语义清晰度更依赖使用者经验

### OPA

- 主要是 Rego 策略语言
- 极其灵活，但并不为 ReBAC 做专门约束

这带来一个很现实的权衡：

- 约束强的 schema，前期不够自由，但长期更容易治理
- 自由度高的策略语言，前期表达快，但长期更容易分叉

对一个十几人团队和对一个上百服务的平台团队来说，这个权衡的答案往往不一样。

## 四、条件能力

### OpenFGA

- 支持 conditions
- 条件附着于 relationship tuple
- 很适合做 ReBAC + ABAC 混合模式

### SpiceDB

- 支持 caveats
- caveated relationship 是一等能力
- 对上下文和关系实例结合得比较自然

### Casbin

- 可通过 matcher 和 ABAC 模型表达条件
- 灵活，但一致语义和 explain 边界需要自己把握

### OPA

- 条件能力极强
- 但条件不是附着在 tuple 语义上的，而是策略求值本身的一部分

如果你现在关注的是“ReBAC + ABAC 混合模式”，这一维尤其重要。  
OpenFGA / SpiceDB 倾向于把条件附着在关系实例上，让条件成为关系成立的约束；  
OPA 则更像把条件放在决策逻辑本身里。  
两者都能做条件，但它们对“条件到底属于关系事实，还是属于策略逻辑”的回答并不一样。

## 五、校验引擎能力

### OpenFGA

- 面向 FGA 场景
- `Check`、`ListObjects`、`ListUsers` 都是体系内能力

### SpiceDB

- 更强调作为权限数据库/服务进行关系求值
- 一致性与 caveat 语义比较完整

### Casbin

- 核心是 enforcer + matcher
- 在单体或服务内嵌场景很方便
- 复杂多跳关系和大规模一致性更多依赖使用方式

### OPA

- 更强在 policy decision
- 对“关系图求值 + tuple 事实层 + 列表语义”不是天然全包方案

这说明一个很关键的工程事实：  
当系统的问题核心是“证明关系是否成立”时，专门的 FGA 引擎会更占优势；  
当系统的问题核心是“根据上下文执行策略决策”时，通用策略引擎会更自然。

## 六、`Check / ListObjects / ListUsers` 能力

这一维非常关键，因为它直接决定系统是否只是“会做 check”，还是能成为真正完整的授权底座。

### OpenFGA

- 三类能力都作为标准能力存在

### SpiceDB

- `CheckPermission`、`LookupResources`、`LookupSubjects` 路线完整

### Casbin

- 更偏 `enforce`
- 列表/反向查询能力更多依赖业务侧补足或自行组合

### OPA

- 强在策略判断
- Data Filtering 可以覆盖一部分搜索型问题
- 但它不是天然的 ReBAC list semantics 服务

这里不能只看“能不能做”，而要看“默认是否正确”。  
对 OpenFGA / SpiceDB 来说，`Check / ListObjects / ListUsers` 本来就是同一个问题的不同入口；  
对 Casbin 和 OPA 来说，这个统一性更多要靠业务方额外设计。  
这就是为什么很多团队会在早期误以为“能做 enforce 就够了”，后期才发现列表问题才是真正把系统拉复杂的地方。

## 七、一致性策略

### OpenFGA

- 提供 consistency mode 概念
- 允许调用方在延迟与新鲜度之间做选择

### SpiceDB

- 这一维非常强
- `ZedToken`、多种 consistency level、watch/revision 都比较成熟

### Casbin

- 一致性更多取决于接入模式和底层存储
- 如果是嵌入式模式，分布式一致性通常要靠业务自己设计

### OPA

- 更像策略执行节点
- 数据新鲜度依赖 bundle、sidecar 输入、外部同步机制

所以如果一个团队把“一致性边界”视为选型重点，那么 SpiceDB 往往会显得最像数据库产品，OpenFGA 更像标准化 FGA 服务，Casbin 和 OPA 则需要更多外围补足。  
这不是优劣，而是产品定位差异。

## 八、多节点与高可用

### OpenFGA

- 作为服务部署时更容易统一控制面和数据面

### SpiceDB

- 明确面向分布式部署与高频权限查询
- 文档中对 datastore、一致性和 watch 的讨论都较充分

### Casbin

- 非常适合库式嵌入
- 但如果要做成集中式高可用授权服务，需要自己补齐更多外围基础设施

### OPA

- 在 sidecar、proxy、microservice 模式下非常灵活
- 但它的高可用重点在策略执行层，而不是完整 ReBAC 事实层

从高可用角度看，这几类项目其实落在两条路线：

- 中央授权服务 / 权限数据库路线
- 分布式策略执行 / 嵌入式执行路线

前者更容易统一语义与一致性，后者更容易贴近流量、降低调用成本。  
你选的其实不只是一个项目，而是一种系统拓扑。

## 九、调试与 Explain

### OpenFGA

- 模型清晰、语义清楚，比较适合构建 explain 工具链

### SpiceDB

- 对 caveat、consistency、watch 等运行时能力讨论更细，利于解释复杂场景

### Casbin

- 容易嵌入，但 explain 能力更多取决于业务层如何封装

### OPA

- policy trace 和决策输出能力强
- 但如果关系事实系统不统一，explain 仍然可能碎片化

这也是 explain 最容易被误解的地方。  
解释能力不只是“打印执行日志”，而是系统能否把：

- 事实来源
- 关系传播
- 条件判断
- 一致性边界

放在同一个解释模型里。  
在这方面，问题域越专门的产品，通常越容易做出强解释能力。

## 十、适用场景与边界

### OpenFGA

适合：

- 需要完整 FGA 服务
- 重视标准语义和建模清晰度

### SpiceDB

适合：

- 明确要走 Zanzibar 风格
- 对一致性、关系规模和服务化能力要求较高

### Casbin

适合：

- 想快速在应用内集成授权
- 场景更多是库式使用，而不是独立权限数据库

### OPA

适合：

- 需要通用策略执行
- 微服务、网关、Kubernetes、合规策略
- 想把“策略决策”和业务逻辑分离

如果再把这一节说得更实用一点，可以这样记：

- OpenFGA：你想要一套标准化细粒度授权服务
- SpiceDB：你想要一套更像权限数据库的 Zanzibar 路线
- Casbin：你想把授权能力快速嵌入应用
- OPA：你想把策略判断广泛铺到网关、平台和执行边界

## 十一、接入复杂度

### OpenFGA / SpiceDB

- 初次建模门槛更高
- 但一旦系统复杂度上来，长期结构更清晰

### Casbin

- 上手快
- 集成轻
- 但复杂关系场景下，需要团队自己把边界守好

### OPA

- 对策略化团队非常友好
- 但如果你真正要的是完整 ReBAC 基础设施，仅用 OPA 往往不够

很多误选都发生在这一节。  
常见错误不是“选了差的项目”，而是：

- 用 OPA 去承担完整关系事实层
- 用 Casbin 去承担分布式一致性授权底座
- 用 OpenFGA/SpiceDB 去解决纯策略编排问题

项目本身没错，错的是问题和工具没有对齐。

## 十二、生态成熟度

### OpenFGA

- FGA 语义和文档体系成熟

### SpiceDB

- Zanzibar 路线鲜明
- 社区对 consistency、watch、caveat 等细节讨论较深

### Casbin

- 生态广
- 模型覆盖多
- 语言支持多

### OPA

- CNCF 成熟项目
- 策略生态很强
- 已广泛进入云原生基础设施

## 十三、设计哲学差异：它们到底分别相信什么

如果把上面十二个维度再往下压一层，会发现这几个项目其实分别代表了不同的工程信仰：

### OpenFGA 相信“标准化细粒度授权服务”

它的设计更强调：

- 标准化 DSL / API
- 明确的模型和 tuple 边界
- 统一的 `Check / ListObjects / ListUsers`

这种路线对平台化团队非常友好，因为它把“怎么做细粒度授权”尽量固化成了一套通用答案。

### SpiceDB 相信“权限是一类专门的数据系统”

它更像是把 Zanzibar 路线往“权限数据库”方向推得更深：

- revision
- watch
- caveat
- relationship

这些概念都很强地体现了数据系统思维。

### Casbin 相信“授权应该尽量可嵌入、可组合”

它更像一个能力框架，强调：

- 灵活模型
- 多语言
- 快速集成

代价是很多大型系统真正关心的“统一语义”和“分布式一致性”不会自动从框架里长出来。

### OPA 相信“策略决策应该从业务代码中抽离”

它最核心的价值不在 ReBAC，而在：

- 策略即代码
- 通用决策
- 平台执行边界统一治理

它非常强，但强的地方并不等于“天然就是完整关系授权底座”。

## 十四、最典型的误选场景

这一节对真正做选型的人往往最有用，因为很多错误都是可预测的：

### 误选一：团队只有岗位权限，却上了完整 FGA 服务

结果通常是：

- 建模过重
- 维护成本高
- 团队觉得“这套系统太复杂”

问题不在工具，而在需求还没到那个复杂度。

### 误选二：系统已经是复杂协作场景，却还坚持只用嵌入式 enforce

早期看起来很轻，后期会快速遇到：

- 列表语义不统一
- 反向查询困难
- 多服务授权漂移
- 一致性能力缺失

### 误选三：把 OPA 当作关系授权数据库

OPA 很强，但如果团队真正缺的是：

- tuple 事实层
- userset 传播
- 一致性 token
- watch / changelog

那只用 OPA 往往会迫使团队自行补出半套 FGA 系统。

## 十五、一个更成熟的现实答案：它们常常不是互斥的

真正成熟的平台里，这几类能力经常会组合出现，而不是单选题。

例如：

- OpenFGA / SpiceDB 负责关系授权底座
- OPA 负责网关、平台和合规策略
- Casbin 负责某些局部嵌入式快速授权场景

换句话说，选型问题有时不是“谁替代谁”，而是“谁应该占据哪一层”。

## 一个最实用的选型结论

如果你的目标是：

- 做一套完整细粒度授权底座
- 强调关系语义
- 同时关心 `Check / ListObjects / ListUsers`
- 还关心一致性与多节点问题

那么 **OpenFGA / SpiceDB** 通常更接近目标。

如果你的目标是：

- 在应用内快速嵌入一套可配置授权模型

那么 **Casbin** 往往更轻。

如果你的目标是：

- 做策略执行层
- 解耦微服务授权逻辑
- 做上下文策略和数据过滤

那么 **OPA** 更适合作为策略引擎。

## 本文小结

最重要的结论只有一句：

**不要把 OpenFGA、SpiceDB、Casbin、OPA 当成功能完全对等的替代品。**

它们分别代表：

- FGA 服务
- Zanzibar 风格权限数据库
- 嵌入式授权框架
- 通用策略引擎

真正正确的选型，不是比谁“更强”，而是先回答：  
你要解决的到底是**关系授权问题**、**嵌入式授权问题**，还是**通用策略执行问题**。

如果一个团队已经理解了上述模型与工具差异，应该如何把 `ACL / RBAC / ABAC` 系统性地落进一套 ReBAC 底座？
