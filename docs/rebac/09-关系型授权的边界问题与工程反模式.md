# 09. 关系型授权的边界、问题与工程反模式

## 为什么谈边界比谈能力更重要

任何技术路线在刚被广泛接受时，最容易出现的误区就是：

- 把它看成万能答案

ReBAC 也不例外。  
它的确非常适合复杂协作和细粒度授权，但这不等于：

- 所有系统都应该改造成 ReBAC
- 所有授权问题都应该建成关系图
- 一旦用了 ReBAC，一致性和高可用就自动解决

真正专业的工程判断，必须同时看到它的强项和边界。

![ReBAC 适用边界示意图](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/11-rebac-boundaries.svg)

## ReBAC 最适合的场景

### 1. 复杂协作

例如：

- 文档、目录、项目、群组
- B2B 共享
- 跨组织协作

### 2. 层级传播明显

例如：

- organization -> project -> resource
- folder -> document

### 3. 列表查询很重要

系统不仅要回答：

- 能不能访问

还要回答：

- 能访问哪些对象
- 哪些主体能访问这个对象

### 4. 需要高可解释性

例如：

- 审计
- 安全合规
- 平台级问题排查

## 哪些场景不必强上 ReBAC

### 1. 纯后台岗位授权

如果系统几乎只有：

- 菜单
- 按钮
- 稳定岗位

那么 RBAC 往往已经足够。

### 2. 没有复杂资源图

如果对象之间基本没有层级传播，也没有群组、owner、继承等复杂关系，那么引入 ReBAC 的收益可能不高。

### 3. 极低变更、极低规模、极低动态性系统

这种系统可能用 ACL 或 RBAC 就足够稳定。

## ReBAC 常见的工程问题

## 1. 模型过抽象

最常见的问题之一，就是刚开始建模时过度抽象，试图一套 meta-model 表达所有业务对象。

例如：

- 一个 `resource`
- 一个 `relation`
- 一个 `entity`

看似通用，实际上：

- 类型边界变模糊
- list 查询更难
- 模型难读难审
- 团队更难维护

OpenFGA 官方也明确反对过度 meta-model 化，推荐“建你的领域模型，而不是万能模型”。

## 2. 关系和条件职责混乱

另一个常见问题，是把本该用关系表达的东西写成条件，或者反过来。

正确的判断标准是：

- 结构性归属、传播、成员关系 -> 用关系
- 运行时上下文、环境约束 -> 用条件

如果这条边界不清晰，模型会越来越难懂。

## 3. 把查询仓储当最终授权答案

有些系统为了性能，会直接把某些 tuple 查询结果当作授权结果返回。  
这样做短期看很快，长期会带来两个后果：

- 跳过传播语义
- 跳过条件、过期和一致性边界

最终“看起来像答案”，实际只是事实切片。

## 4. 用多套逻辑解决同一个语义问题

这是最危险的反模式之一：

- 接口 `check` 一套
- 页面列表一套
- 搜索过滤一套
- 导出一套

一旦发生这种分裂，授权系统迟早会进入“不同入口不同答案”的状态。

## 5. 过度依赖缓存，低估一致性代价

缓存是必须的，但如果团队只看：

- 命中率
- 延迟

而忽视：

- 数据新鲜度
- revision/token
- 缓存失效边界

那么权限系统很容易在最敏感的时候返回旧结果。

## ReBAC 当前仍然存在的现实代价

即便是成熟路线，ReBAC 也依然有现实代价：

### 建模门槛更高

团队需要重新学习如何从业务对象出发建模，而不是只会定义角色。

### 引擎实现复杂

需要：

- compiled model
- evaluator
- recursion guard
- cache strategy
- consistency token

### 观测和调试要求更高

没有 explain 和测试支撑时，系统会非常难排错。

### 列表查询依旧是难点

即使在成熟系统里，`ListObjects / ListUsers` 通常也比单次 `check` 更难做、更难优化。

## 开源项目是怎么面对这些边界的

### OpenFGA

通过明确的模型原则、不可变模型版本、统一 API 和 condition 机制来降低错误建模概率。

### SpiceDB

通过 revision、watch、caveat 和强执行语义，把 correctness 问题放到系统中心。

### Casbin

更灵活、更容易嵌入，但也意味着大规模一致性、事件同步和多节点语义一致性更多要由业务侧自己承担。

### OPA

非常适合策略执行和上下文规则，但如果要把它单独拿来解决完整 ReBAC 问题，往往还需要额外事实层和关系语义承载系统。

## 五个工程反模式

这里把最值得警惕的反模式集中列出来：

1. **全靠 SQL Join**  
   把传播逻辑和关系求值全部塞进 SQL，最终可维护性往往极差。

2. **模型和 API 双真相**  
   模型说一套，写入接口暴露另一套，最终系统不可解释。

3. **条件滥用**  
   用条件表达结构问题，而不是上下文问题。

4. **多套校验链路**  
   `check`、列表和导出不共享同一语义。

5. **项目实现被误当行业规律**  
   某个系统里的折中做法，不代表 ReBAC 通用最佳实践。

## ReBAC 最大的边界到底是什么

如果一定要用一句话概括 ReBAC 的最大边界，那就是：

**它解决的是“关系驱动授权”的问题，不是所有策略问题的总和。**

这句话意味着：

- 它不替代认证
- 它不替代风控
- 它不替代策略引擎
- 它不替代业务工作流

但它可以成为这些能力之中，负责“授权关系语义”的那一层中枢。

## 本文小结

你可以带走五条判断：

1. **ReBAC 很强，但不是所有系统都值得为它付出复杂度代价。**
2. **它最适合关系传播复杂、协作密集、列表语义重要的系统。**
3. **它最常见的问题不是能力不足，而是建模失真和执行边界不清。**
4. **缓存、一致性和 explain 没处理好，再强的模型也会翻车。**
5. **专业团队不只会讲 ReBAC 能做什么，也必须清楚它不该做什么。**
