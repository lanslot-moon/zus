# 06. 关系型授权校验引擎设计

## 为什么权限系统的难点不在“能不能 check”

很多团队第一次做权限系统时，会天然把核心目标理解成：

- 给定用户、对象、动作
- 返回 true / false

这当然是必须的，但它只覆盖了最简单的一类问题。  
真实系统很快还会问：

- 这个用户能看到哪些对象
- 哪些用户能访问这个对象
- 某次判断为什么通过
- 为什么刚写完权限马上读不到

一旦这些问题进入系统，权限引擎就不再是一个单点判断函数，而是一个完整的语义执行系统。

## `Check / ListObjects / ListUsers` 为什么必须统一

这是现代 ReBAC 系统最关键的设计原则之一。  
很多系统失败，恰恰就是因为这三条链路是分开实现的。

### `Check`

问的是：

- 给定 subject、object、relation，授权是否成立

### `ListObjects`

问的是：

- 给定 subject 和 relation，哪些 object 成立

### `ListUsers`

问的是：

- 给定 object 和 relation，哪些 subject 成立

它们的输入看起来不同，但语义完全同源：  
都是在同一个模型和同一组事实之上做证明。

如果分开实现，就会非常容易出现：

- API `check` 通过，但页面列表看不到对象
- 页面列表能看到对象，但点进去再被拒绝

这类问题不是“前端调用错了”，而是语义内核被拆裂了。

## 一个统一 evaluator 的核心职责

统一 evaluator 至少要做五件事：

1. 读取 compiled model
2. 读取 tuple facts
3. 按 rewrite AST 递归求值
4. 处理候选集枚举
5. 提供一致的解释路径

![统一 evaluator 总览](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/06-unified-evaluator.svg)

如果从更专业一点的角度看，evaluator 实际上是在解决一个递归证明问题：

- 当前请求要证明什么
- 这个命题可以拆成哪些子命题
- 哪些子命题需要查 direct fact
- 哪些子命题需要沿 relation 传播
- 哪些子命题已经证明过或已经失败过

换句话说，evaluator 不是“调几个 repository 然后拼结果”，而是一个受限的证明机。

## 一个成熟 evaluator 的内部状态应该是什么

如果只把 evaluator 的入参理解成：

- subject
- object
- relation

那么很多运行时需求就会无处安放。  
真正的执行上下文通常还至少包含：

- 当前递归深度
- 访问路径
- consistency token / revision
- request context
- memo cache
- explain collector

这也是为什么 `check(subject, object, relation)` 这种极简函数签名，在复杂系统里最后总会被一个 `EvaluationContext` 或 `EvaluationRequest` 替代。  
不是为了“面向对象优雅”，而是因为问题本身需要这些状态。

## 关系节点为什么要有明确的求值语义

如果 rewrite expression 最终只是被解析成一堆字符串分支，那么 evaluator 很快就会膨胀成一个难以维护的大方法。  
更稳的设计是：每种节点有明确语义。

### Self

检查当前对象上的 direct tuple 是否命中当前主体。  
这是最基础的路径，也是命中频率最高的路径。

### Union

任一分支成立即可。  
常见于：

- `viewer = owner or editor or viewer from parent`

### Intersection

所有分支都成立才算命中。  
适合表达复合权限，但代价通常更高。

### Exclusion

左边成立且右边不成立。  
适用于黑名单或排除集模型。

### ComputedUserset

把一个关系映射到同对象的另一关系。  
例如：

- `editor = owner`

### TupleToUserset

先根据一条 tuple 找到目标对象，再在目标对象上求值。  
这是 ReBAC 层级传播的核心能力。

## 为什么节点语义最好做成“模板 + 策略”而不是巨型分支

很多自研引擎一开始都能写出能跑的版本，但很快会在一个方法里堆满：

- 如果是 self
- 如果是 union
- 如果是 exclusion
- 如果是 tuple-to-userset
- 如果这是 listObjects 模式
- 如果要带 explain

最后形成一个三四百行、几乎不敢改的方法。  
这类代码的核心问题不是长，而是它把三层职责压在了一起：

- 递归模板
- 节点语义
- 查询方向差异

更稳的拆法通常是：

- 模板方法统一管理递归、memo、循环检测、explain
- 节点策略负责单类 rewrite 节点的求值
- 查询方向策略处理 `Check / ListObjects / ListUsers` 的入口差异

这样做最大的收益不是“模式用得漂亮”，而是每次增加一种语义时，不需要再碰整个执行主循环。

## 为什么递归、memoization 和循环检测是硬需求

### 递归是能力来源

没有递归，很多关键模型都无法优雅表达：

- group 嵌套 group
- folder 递归 parent
- organization -> project -> document 级联传播

### 递归也是风险来源

一旦模型存在回环或者异常传播链，没有保护机制，系统会迅速陷入：

- 无限递归
- 重复求值
- 高延迟
- 高 CPU

因此 evaluator 必须具备：

#### 深度限制

防止异常模型导致无限展开。

#### 访问路径跟踪

记录当前正在展开的路径。

#### 循环检测

如果某个节点已经在当前路径中，就及时终止。

#### Memoization

把已经求过的子问题缓存起来，避免反复计算。

更进一步说，memoization 的 key 也不能太随意。  
如果 key 只包含：

- subject
- object
- relation

那么在下面这些场景里就会出现错误复用：

- 同一命题在不同 consistency token 下被复用
- 同一命题在不同 request context 下被复用
- 同一命题在不同 depth / path 约束下被复用 explain

因此更稳妥的 key 至少要体现：

- 逻辑命题本身
- 新鲜度边界
- 条件上下文哈希
- 必要的执行模式

这是很多系统前期不太注意、后面才发现“缓存明明命中了，结果却解释不通”的根源。

## 候选裁剪为什么重要

`Check` 是单个请求。  
`ListObjects` 和 `ListUsers` 则天然有搜索属性。

这意味着真正的难点通常不是最后那一步 `evaluate`，而是：

- 到底应该从哪些对象开始尝试
- 到底应该从哪些主体开始尝试

如果直接全量扫描对象再逐个 `check`，在大规模系统里几乎不现实。

因此成熟实现通常会把责任分开：

- 仓储负责给出**候选集**
- evaluator 负责给出**最终结论**

这样可以兼顾：

- 持久层优化空间
- 语义统一
- 结果正确性

这里还有一个常被忽略的判断：

**候选裁剪不是为了偷懒少算，而是为了把“搜索空间”从授权语义里剥离出去。**

这句话很重要。  
因为 `ListObjects`、`ListUsers` 的困难点不只在“枚举很多”，而在于：

- 搜索空间可能无限接近业务全集
- 真正命中的对象往往只占很小一部分
- 传播路径可能跨多层关系

因此仓储层更适合提供：

- direct match 候选
- link relation 候选
- 基于 subject 或 object 的反向候选

而 evaluator 再在这些候选之上做最终语义证明。  
如果把两者混在一起，通常会出现两个极端：

- 为了正确性，全表扫后逐个 `check`
- 为了性能，仓储直接返回“看起来像答案”的结果

这两种极端都不稳。

## 条件求值在引擎中应该放在哪一步

这也是一个很容易做歪的点。

更稳妥的执行顺序通常是：

1. 模型先判断这个 relation 允许 direct/self 命中
2. tuple 先匹配 subject、object、relation
3. 再判断 wildcard / expires / restriction
4. 最后判断 condition 是否成立

也就是说，条件不是替代关系命中的前提，而是关系命中后的上下文过滤器。

这样做的好处是：

- evaluator 的责任边界清楚
- condition 可以复用
- conditional tuple 与 normal tuple 的执行顺序一致

## Explain 为什么不是“锦上添花”

复杂权限系统一旦没有 explain，很快就会在运维和排错上变得痛苦。  
最基本的 explain 能力应该让调用方或开发者回答：

- 这次授权为什么通过
- 是 direct tuple 命中的，还是传播得到的
- 哪条路径命中了
- 如果失败，是哪个分支失败了
- 是因为条件失败，还是因为 consistency 读到了旧快照

没有 explain 的系统，最终往往会把大量时间花在“猜测为什么这个判断错了”上。

更成熟的 explain，甚至应该能回答结构化问题：

- 命中了哪种节点
- 进入了哪条 relation 链
- 哪个 direct tuple 参与了证明
- 哪个 condition 失败了
- 因为哪个 token/快照边界导致看不到最新数据

这意味着 explain 最好不是一段自由文本，而是一棵有层次的解释树。  
文本只是最终展示层，解释结构本身应该能被程序消费。

## 复杂度为什么会在 ReBAC 引擎里突然爆炸

很多开发者第一次做 evaluator 时，会低估它的复杂度，因为每个局部规则看起来都不难。  
真正的复杂度来自几个因素叠加：

- relation 嵌套
- 资源层级
- group 嵌套
- reverse lookup
- 条件过滤
- 候选枚举

这意味着 `Check` 的最坏情况并不是一个常量时间问题，而更接近“受模型形状、关系密度和候选集大小共同影响”的搜索问题。  
因此 evaluator 设计里，所有这些看似“工程技巧”的能力其实都不是可选项：

- 深度限制是为了封住异常扩张
- memoization 是为了避免重复证明
- 候选裁剪是为了限制搜索空间
- explain 是为了让复杂搜索可调试

## 开源实现给出的共同经验

不论是 OpenFGA 还是 SpiceDB，它们最终都没有把授权引擎做成“一个大 if/else 函数”，而是围绕几个共同原则演进：

- 关系语义必须稳定
- 列表能力不能和 check 脱节
- 一致性边界必须进入执行上下文
- 运行时必须能解释自己的证明路径

这些经验背后说明的其实是同一件事：  
ReBAC evaluator 不是普通业务代码里的一个 service，它更像一个小型查询与证明内核。

## 工程上最容易犯的 4 个错误

1. 把 evaluator 写成一大坨 `if/else`
2. `Check / ListObjects / ListUsers` 分三套逻辑
3. 把候选查询直接当成最终授权答案
4. 没有深度限制与循环检测

这四个错误中，只要命中两个，系统后续维护成本通常都会显著上升。

## 本文小结

统一 evaluator 的价值，不只是代码复用，而是**语义统一**。  
你可以带走下面四个结论：

1. **`Check / ListObjects / ListUsers` 本质是同一语义问题的三个入口。**
2. **递归、memoization、循环检测和深度限制是 ReBAC 引擎的基本功。**
3. **仓储负责候选，evaluator 负责结论，这是性能与正确性的平衡点。**
4. **Explain 能力不是附加功能，而是复杂授权系统的生存工具。**

下一篇我们继续进入最现实也最容易出问题的话题：  
多节点、多缓存、多副本环境下，权限系统如何尽量保证读到的是“足够新”的数据。
