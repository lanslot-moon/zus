# 04. 资源关系如何建模与存放

## 为什么“关系放哪里”是权限系统的关键问题

很多权限系统失败，并不是失败在“模型不够先进”，而是失败在**授权事实被存得太散**。

常见的散落方式包括：

- 用户角色表里有一部分事实
- 资源表里有一部分 owner 字段
- 群组关系在另一张表
- 外部共享放在单独表里
- 临时授权写在缓存或脚本里

这样做的最大问题是：  
系统很难回答“当前真正的授权事实到底是什么”。

而现代 ReBAC/FGA 路线最重要的一个工程选择，就是把授权事实尽量收敛到统一 tuple 结构中。

## 为什么 tuple 值得成为事实层

tuple 的吸引力不在于它“简单”，而在于它天然具备三种工程价值：

1. **统一性**：无论 direct 授权、组成员关系、父对象关系，本质都能落成关系事实
2. **可传播性**：模型可以在 tuple 之上定义传播规则
3. **可审计性**：所有关系事实都具有统一结构，变更更容易追踪

可以把 tuple 理解为一种标准化的关系原子。

## 一个最基础的 tuple 长什么样

从抽象视角看，tuple 至少表达三件事：

- `subject`
- `relation`
- `object`

例如：

- `user:alice#viewer@document:doc-1`

但如果只停留在这三元组层面，系统还很难支撑现代 FGA 场景。  
因此真实系统通常会继续扩展 tuple 结构。

## 现代 FGA 系统里的事实层通常包含什么

### Subject 与 Object

它们分别表示：

- 被授权主体
- 被访问对象

通常需要显式区分：

- `type`
- `id`

这样做的原因是，不同对象类型本来就应该承载不同关系语义。

### Relation

关系本身不是任意字符串，而应受模型约束。  
它表达的是某个对象类型上可被授予或可被推导的关系名。

### Subject Relation

这部分经常被低估，但它是 userset 建模的关键。  
当 subject 不是单个用户，而是某个对象上的一组关系集合时，`subject_relation` 就变得必要。

例如：

- `group:eng#member`

这里真正被引用的不是 group 对象本身，而是它的 `member` userset。

### Wildcard

现代系统里常常需要表达“所有用户都可以看”这样的语义。  
如果每次都展开成全量用户写入，显然不现实。

因此很多系统会引入：

- `user:*`

或者显式字段 `is_wildcard`，以支持“公共可见”这类模型。

### Expires

临时授权是非常典型的现实需求：

- 分享链接 24 小时有效
- 审计员 7 天内可读
- 代理处理人一周后失效

如果没有 `expires_at`，这些能力就会退化为额外脚本或人工清理任务。

### Condition

当 ReBAC 需要和 ABAC 混合时，tuple 上通常还要承载条件信息：

- condition template reference
- condition context

这样条件就附着在关系事实上，而不是浮在系统外层。

### Consistency Token / Revision / Zookie

如果系统存在多节点、多缓存、异步副本，那么读操作到底看到哪个时点的数据，就必须成为事实层或请求上下文的一部分。

这就是为什么 Zanzibar 有 `zookie`，SpiceDB 有 `ZedToken`，很多自研系统也会引入 revision/version token。

## Tuple 和 Userset 为什么经常一起出现

ReBAC 的真正力量不只在于 direct tuple，还在于 tuple 能引用 userset。

例如：

- `document:doc-1#viewer@group:eng#member`

这条事实的意思不是“group:eng 这个对象本身是 viewer”，而是：

- `eng` 组的所有 `member`
- 都是 `document:doc-1` 的 `viewer`

这类建模方式带来两个直接收益：

1. 不需要把组成员全部展开写进文档授权表
2. 当组成员变化时，文档可见性可以随成员关系自动变化

这正是 ReBAC 统一关系语义的关键价值之一。

## 为什么很多系统最终会选择“结构化存储 + 图式求值”

不少团队初次接触 ReBAC 时会以为：

- 既然是关系图，是否应该直接用图数据库？

这并不是唯一答案。

事实上，像 Zanzibar/OpenFGA/SpiceDB 这一类路线的关键，不是必须采用图数据库，而是：

- 用结构化关系存储持久化事实
- 用编译模型和 evaluator 在查询时做图式传播和求值

这种做法的现实优势在于：

- 存储侧成熟
- 索引可控
- 变更、事务、审计更容易设计
- 不需要把全部复杂性都压进数据库引擎

## 事实层设计中的几个关键权衡

### 权衡 1：是否把 owner 单独放在资源表

很多业务对象天然有 owner 字段。  
从业务表设计看，这很常见；但从授权系统设计看，最好仍然考虑将 owner 同步进 tuple 层，避免事实双写导致语义漂移。

### 权衡 2：是否允许模型外事实存在

如果模型里没有定义 relation，但事实层却允许写入这类 relation，系统迟早会不可解释。  
因此事实层应该始终受到模型约束。

### 权衡 3：是否提前展开传播结果

为了性能，有些系统会尝试把传播关系直接展开成冗余事实。  
这在某些只读或搜索场景里可以作为优化，但不能替代源事实本身，否则模型会和事实层混在一起。

## 面向读写分离的设计建议

如果系统将来需要：

- 高频 `check`
- 列表查询
- watch
- 多节点部署

那么事实层设计时最好从一开始就明确区分：

### 写侧职责

- 写入 direct tuple
- 删除或更新 tuple
- 记录变更日志
- 维护 version/revision

### 读侧职责

- direct tuple 查询
- link tuple 查询
- 候选 object 查询
- 候选 subject 查询

注意：  
读侧仓储应该负责提供**候选事实**，而不应该在仓储层直接给出最终授权结论。  
最终授权结论应仍由 evaluator 统一产出。

## 一个开发者最容易踩的坑

设计事实层时，最容易犯的错误不是字段少，而是**把太多授权含义拆散到多个异构表和多个业务语义里**。  
一旦这么做，后面的模型传播、列表查询和一致性控制都会变得异常困难。

## 本文小结

你可以带走四个核心结论：

1. **tuple 的价值是统一授权事实，不是单纯做一张关系表。**
2. **userset、wildcard、expires、condition、revision 都是现代 FGA 事实层的重要组成。**
3. **图是语义，结构化关系存储仍然可以很好地承载事实层。**
4. **写侧负责维护事实，读侧负责提供候选，最终语义仍应交给 evaluator。**
