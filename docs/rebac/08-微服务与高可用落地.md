# 08. 微服务与高可用落地：关系型授权作为基础设施怎么建设

## 当 ReBAC 不再只是一个库，而是一项基础设施

在很多小系统里，授权逻辑会以内嵌库的方式存在：

- 应用自己持有角色和权限表
- 应用自己做判断

但当系统进入多团队、多服务、多租户和高频授权场景时，这种做法会迅速面临几个问题：

- 各服务的授权语义漂移
- 各服务的数据事实不一致
- 策略更新难以统一发布
- 列表查询与单点校验无法共享语义

于是 ReBAC 会逐渐从“某个应用内部能力”，演变成一个**独立授权基础设施**。

## 为什么微服务环境会放大权限问题

微服务会把原本单体里的授权问题切碎到多个边界：

- 资源数据属于不同服务
- 身份上下文来自统一身份系统
- 业务操作通过网关、BFF、服务间调用、异步任务共同完成
- 一次用户动作可能穿过多个服务

如果授权没有独立出来，常见结果是：

- 每个服务各自缓存一套权限判断
- 各自维护一份简化规则
- 接口间对同一关系的理解不同

高可用和正确性问题往往由此开始。

## ReBAC 基础设施通常如何分层

比较稳妥的思路，是把 ReBAC 服务拆成两个逻辑面：

### 控制面

负责：

- 管理模型
- 管理 schema / DSL
- 管理模型版本发布
- 提供运维、审计与可视化管理能力

### 数据面

负责：

- tuple 写入
- `check / listObjects / listUsers`
- revision / token
- watch / changelog
- 高性能读取

![ReBAC 高可用部署拓扑](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/08-microservice-ha.svg)

这样分层的好处是：

- 模型管理和高频读请求解耦
- 发布流程和运行时流量解耦
- 更容易为不同面做不同的扩缩容策略

在更大一点的组织里，这种分层还有一个容易被忽略的价值：  
它把“模型治理”和“流量承载”从同一团队的临时脚本中剥离出来，变成了两个可以独立演进的能力面。  
否则很容易出现一种典型局面：

- 业务急着改规则
- 平台担心运行时抖动
- 发布流程和查询流量互相牵扯

最后谁都不敢动。

## 高可用设计的几个关键点

## 1. 计算节点必须无状态或尽量无状态

如果授权服务节点持有太多不可替代的本地状态，那么故障切换会非常困难。  
成熟实现通常会让节点：

- 只持有可重建缓存
- 依赖外部持久化事实层
- 依赖外部或共享一致性边界

这样节点宕机后，可以被快速替换。

## 2. 模型缓存与关系缓存要区分

这是高可用设计里很容易被忽视的一点。

### 模型缓存

适合按 `store + model version` 缓存，变更频率相对低。

### 关系缓存

命中频率高、失效频率也高，更依赖 revision/token/watch。

把两者混成一个“大授权缓存”，通常会让失效逻辑非常混乱。

## 3. 副本和只读节点适合承担什么

在高读场景下，很多系统会考虑：

- 主库写
- 只读副本读

这条路径不是不能做，但要清楚它的代价：

- 延迟复制会带来旧数据风险
- 强一致读会变慢

因此，副本读是否适合用于权限判断，取决于：

- 请求对新鲜度的要求
- 是否带 token
- 是否允许短暂陈旧

## 4. 故障转移不能只看“服务是否存活”

授权系统的故障转移，不只是服务存活问题，还包括：

- 故障节点上的缓存是否会造成错误结果
- 切换到新节点后是否还能维持足够一致
- watch 消费者断连后是否能续读

因此高可用设计必须同时覆盖：

- 计算节点
- 存储节点
- 事件流
- 缓存层

这其实对应了授权基础设施的一个关键判断：

**高可用 = 进程存活 + 数据可信 + 解释一致。**

如果服务活着，但：

- 节点缓存比 token 老
- watch 消费位置丢了
- 副本滞后过大
- list 接口和 check 接口走的不是同一快照语义

那它虽然“在线”，却不一定真的“可用”。

## 微服务接入 ReBAC 的几种常见模式

### 1. 应用直连授权服务

优点：

- 清晰
- 统一语义
- 调用方简单

缺点：

- 授权服务成为高频依赖
- 延迟敏感

### 2. 网关或 BFF 集中调用

优点：

- 适合统一入口控制
- 可减少部分重复调用

缺点：

- 不适合所有内部对象级细粒度判断
- 容易把授权语义错误上移到边缘层

### 3. Sidecar / Library / Local Proxy

优点：

- 更靠近调用方
- 延迟低

缺点：

- 一致性和缓存失效设计更复杂
- 部署和版本管理更麻烦

不同模式没有绝对标准答案，但有一个很重要的原则：

**无论调用路径在哪里，最终授权语义都应该来自统一模型和统一 evaluator，而不是各服务自己“复刻”一份。**

这里最值得警惕的是 Sidecar 和本地库模式带来的“便利幻觉”。  
它们往往在单服务视角下看起来很好：

- 延迟低
- 本地调用简单
- 服务自治感强

但一旦组织规模扩大，就会暴露出几个问题：

- 每个节点的模型版本是否同步
- 每个节点的关系缓存是否追平
- 每个节点是否都实现了相同的 explain 和 consistency 语义
- 发生故障时，问题是在业务服务、sidecar 还是事实层

所以 Sidecar 并不是不能用，而是它把“中央复杂度”换成了“边缘复杂度”。

## 高可用与性能之间最真实的冲突

把 ReBAC 做成基础设施之后，你很快就会遇到一个永恒冲突：

- 更快
- 更准
- 更省

三者几乎不可能同时最优。

例如：

- 开更多缓存，性能更好，但一致性窗口更难控
- 读主库强一致，正确性更强，但延迟和成本更高
- 在边缘本地做结果缓存，吞吐更高，但语义漂移风险更大

这意味着 ReBAC 的高可用设计，本质上就是一套面向风险和成本的权衡设计。

如果把这些权衡落到实际 SLA，通常会形成非常具体的分层：

- 普通读：强调低延迟和较高可用
- 刚写后读：强调新鲜度
- 风险操作前校验：强调正确性
- 审计与回放：强调可重建和可解释

也就是说，授权系统未必需要让所有 API 都追求相同等级的一致性和延迟。  
真正成熟的做法，是先承认不同请求的风险级别不同，再为它们配置不同的读路径和缓存策略。

## 多区域和容灾为什么会把问题再放大一层

一旦 ReBAC 从单集群走向多可用区，甚至多地域，之前很多“勉强还能靠经验压住”的问题都会被放大：

- 跨区域复制延迟
- 时钟偏差
- token 是否跨区域可比较
- watch 是否支持断点续读
- 故障切流后缓存是否还能可信

这也是为什么很多真正大规模的授权系统，最终都会把重点放在：

- revision 可比较性
- 无状态计算节点
- 明确的恢复点
- 事件流续读能力

而不是只在入口层堆更多副本。

## 运维视角下必须补齐哪些观测能力

高可用系统如果没有观测能力，最后只能靠猜。  
对于 ReBAC 基础设施，至少应该有这些指标和诊断面：

- `check / listObjects / listUsers` 的分接口延迟
- consistency mode 分布
- token 追平延迟
- watch 消费落后量
- 缓存命中率与失效率
- explain 采样
- 条件求值失败率

这些指标的价值不只是“监控服务健康”，还在于它们能帮助团队分辨：

- 是事实层变慢
- 是候选集查询失控
- 是 evaluator 扩张
- 还是一致性要求突然升高

## 开源项目在这件事上怎么做

### OpenFGA

倾向于以服务化方式提供统一 FGA 能力，强调模型、tuple 和 API 语义的一致性。

### SpiceDB

强调作为 Zanzibar-inspired 权限数据库运行，提供 revision/token、watch、relationship API 和高性能分发机制。

### OPA

更偏策略引擎和部署灵活性，可嵌入、可 sidecar、可代理扩展，但它并不天然提供完整的 ReBAC 事实层语义。

### Casbin

更偏库式集成和模型灵活性，适合嵌入业务系统，但在超大规模分布式一致性层面通常需要应用自己补足更多基础设施能力。

从这个角度看，几类项目的差异其实很直观：

- OpenFGA / SpiceDB 更像“把授权当作集中式能力面来建设”
- Casbin 更像“把授权能力嵌入到应用内部”
- OPA 更像“把策略决策能力嵌到流量与执行边界上”

这也是为什么它们在高可用问题上的默认答案完全不同。  
不是谁更先进，而是它们解决的问题域不同。

## 本文小结

如果你准备把 ReBAC 作为基础设施来建设，可以带走下面五条判断：

1. **高可用不是只让服务活着，而是让授权结果在故障和切换下仍然可信。**
2. **控制面和数据面最好分层。**
3. **模型缓存和关系缓存一定要分开看。**
4. **副本读、边缘缓存和本地 sidecar 都是有代价的，不只是性能优化。**
5. **无论部署形式如何变化，统一模型和统一 evaluator 都不能丢。**

ReBAC 到底有哪些边界、常见误用和工程反模式。
