# 05. 语法树、图模型与编译链路

## 一个常被忽略的问题：为什么权限系统需要“编译”

很多团队刚开始做权限系统时，会天然觉得：

- 模型配置是文本
- 文本能读懂
- 运行时直接解释文本不就行了

这个想法在简单系统中或许够用，但一旦系统进入高频 `check`、列表枚举、多节点缓存和复杂传播场景，直接解释文本就会出现明显问题：

- 运行时反复解析文本，成本高
- 语法和执行混在一起，难测试
- 节点语义难以复用
- 模型无法稳定缓存

因此，成熟的 ReBAC 系统几乎都会经历同一条链路：

**DSL / 配置文本 -> 结构化模型 -> 编译产物 -> evaluator**

## 为什么还需要 DSL

既然结构化模型更适合机器，为什么还要保留 DSL？

答案很简单：  
因为授权模型同时面向两类读者：

- 人
- 机器

DSL 的价值主要体现在：

- 人类可读
- 易审查
- 易导入导出
- 易做评审和版本 diff

但 DSL 更适合做**表达层**，不适合直接做**执行层**。

## 结构化模型的作用

结构化模型通常是 DSL 的语义化版本。  
它把文本里的定义拆成了更清晰的领域对象，例如：

- type definition
- relation definition
- type restriction
- condition definition

结构化模型的最大价值在于：

- 写侧更容易校验
- API 更容易设计
- 持久化更稳定
- 编译更可控

如果只有 DSL 文本，没有结构化模型，那么模型管理很容易退化成“存一段字符串，然后希望运行时自己解决所有问题”。

## AST 为什么必要

当结构化模型进入执行阶段时，最关键的一步就是把关系重写表达式编译成可执行语义结构，也就是 AST。

可以把 AST 理解为：

- 语法已经被解析
- 节点语义已经被分类
- evaluator 不再需要关心文本写法本身

典型节点包括：

- `Self`
- `Union`
- `Intersection`
- `Exclusion`
- `ComputedUserset`
- `TupleToUserset`

这些节点直接映射到了最终 evaluator 的执行策略。

更重要的是，AST 让系统第一次拥有了一个稳定的“中间语义层”。  
一旦这一层成立，后面的很多能力才会自然出现：

- 节点级单元测试
- 编译时校验
- Explain 树
- 编译缓存
- 模型 diff
- 版本间回滚

如果没有 AST，执行器就只能不断回头解释“原始字符串想表达什么”，整个系统会长期停留在半解释器状态。  
这类系统一开始也许能工作，但越往后越难优化，因为语法、语义、缓存和执行全搅在一起。

## 编译器不只是 Parser 的包装器

很多团队第一次实现授权编译器时，会把它写成：

- 先把 DSL parse 成 parse tree
- 再简单遍历一遍
- 顺手塞进一个运行时对象

这看起来叫“编译”，实际上仍然只是“解析结果搬运”。  
真正有工程价值的编译器，至少还要完成四类工作：

### 1. 语义归一化

例如：

- `this` 和 `self` 是否等价
- `owner or editor or viewer` 是否按统一节点模型展开
- typed wildcard 是否按统一 subject 形式落地

归一化的意义在于，让 evaluator 不必再处理大量“同义但不同写法”的输入。

### 2. 静态校验

编译阶段最值得做的，不是尽量容忍错误，而是尽量早发现错误。  
这类错误包括：

- 引用了不存在的 relation
- `tuple-to-userset` 指向了不存在的 userset
- type restriction 与 relation 目标类型不兼容
- 条件定义存在，但参数约束不完整

如果这些问题拖到运行时才暴露，故障就会从“模型发布失败”升级成“线上请求失败”。

### 3. 可执行形态生成

编译器最终输出的，不应该只是“结构化模型的另一个 DTO”，而应该是带有明确求值边界的只读执行视图。  
也就是：

- relation 已经定位
- rewrite 节点已经分型
- 直接关系与传播关系已经区分
- 运行时查询所需的最小信息已经就位

### 4. 运行时优化前置

成熟实现还会在编译阶段预先组织一些运行时有利的数据结构，例如：

- relation 名称到 compiled relation 的索引
- type 到 relation 的查找表
- condition 定义索引
- userset 引用关系图

这一步的价值在于，把“每次请求都要做的重复查找”前移成“模型变更时只做一次”。

## 图模型和 AST 是什么关系

很多人会把 AST 和图模型混为一谈。  
其实它们解决的问题不同：

### AST 更偏表达式语义

AST 关心的是：

- 关系重写规则如何表达
- 一条 rewrite 语句由哪些节点构成
- 节点之间如何嵌套组合

它更接近“语义树”。

### 图模型更偏传播语义

图模型关心的是：

- subject、object、userset 如何作为节点存在
- tuple 如何成为边
- evaluator 在查询时如何沿边传播和证明

它更接近“运行时关系网络”。

因此更准确的理解是：

- **AST 描述规则**
- **图模型描述事实与传播**

两者不是二选一，而是同一系统里不同层次的表示。

## 为什么 AST 和图模型不能互相替代

这是一个很典型、也很容易被误判的问题。  
有些团队会说：“既然 ReBAC 是关系图，那我只要把所有关系都放进图里搜索不就行了？”  
也有团队会说：“既然 rewrite 已经被 AST 表达了，那运行时直接沿 AST 递归就够了。”

这两种说法都只讲对了一半。

举一个很典型的规则：

```text
document.viewer = owner or viewer from parent_folder
```

这里同时存在两类信息：

- 规则信息：`viewer` 由 `owner` 和 `parent_folder.viewer` 共同构成
- 事实信息：`document:1#parent_folder@folder:9`、`folder:9#viewer@group:team-a#member`

只靠 AST，会知道要先查 `owner`，再查 `parent_folder`，但不会天然拥有实际的关系事实。  
只靠图，会看到节点和边，但不知道 `owner or viewer from parent_folder` 这种组合规则应该如何被解释。

因此系统需要两类视角一起存在：

- AST 告诉你“应该怎么证明”
- 图式事实层告诉你“可以从哪里取证”

一旦把两者混成一个概念，最常见的后果有两个：

1. 把存储层误当执行器，最终写出超复杂 SQL 或图查询
2. 把执行器误当存储层，最终在内存里手搓一个不可控的“全图”

## 一个完整的编译执行链路应该长什么样

![DSL 到执行模型的链路图](/Users/kitona/IdeaProjects/zus/zus-api/docs/rebac/diagrams/exported/05-compiler-pipeline.svg)

这条链路的每一层都有明确职责：

### Parser

负责语法合法性和基本结构解析。

### 结构化模型

负责把语义对象组织成稳定领域结构。

### Rewrite AST

负责把关系传播规则编译成可执行节点。

### Compiled Model

负责给 evaluator 一个只读、稳定、可缓存的执行视图。

### Evaluator

负责将 compiled model 和 tuple facts 组合成最终权限结果。

## 为什么 compiled model 适合做缓存

模型的读取频率通常远低于权限判断频率。  
如果每次 `check` 都重新解析模型，成本太高。

compiled model 的缓存粒度通常适合以：

- `store`
- `authorization model version`

为边界。

它的缓存价值主要体现在：

- 避免重复解析
- 保持执行语义稳定
- 降低 evaluator 初始化成本

前提是编译器本身要足够无状态，否则缓存就会污染请求语义。

## 编译链路里最容易被低估的是“发布边界”

如果把模型编译看成纯技术过程，很容易忽略一个关键事实：

**编译其实是模型发布流程的一部分。**

这意味着编译器不只服务于执行器，还服务于治理流程：

- 模型草稿是否允许保存
- 模型发布前是否必须静态校验通过
- 新版本模型是否立即生效，还是先进入待激活状态
- 老版本 compiled model 是否还能继续为历史请求或旧 token 服务

从这个角度看，compiled model 的缓存粒度也就不只是“性能优化参数”，而是模型生命周期的一部分。  
比较稳妥的做法通常是：

- 用模型版本号作为编译缓存键
- 把“store 当前激活模型”作为另一层映射
- 模型发布只失效该版本缓存
- 模型激活只切换 store 到 model 的指针

这样做的好处是，模型治理和执行缓存之间的边界很清楚，不会因为一次发布把整个运行时状态搅乱。

## 编译时应该拦住哪些错误，运行时又该接受哪些不完美

一个成熟系统不会试图在编译期解决所有问题。  
更现实的划分是：

### 编译期适合解决的

- 语法错误
- 未定义引用
- relation 冲突
- type restriction 明显不成立
- condition 定义不完整

### 运行时仍然必须处理的

- tuple 缺失
- condition context 缺参
- token 过旧或快照不可用
- 递归路径过深
- 分布式副本还未追平

这个划分非常重要，因为它决定了：

- 哪些问题应该在发布前被拒绝
- 哪些问题应该在请求时以 explain 或失败结果体现
- 哪些问题不应再被“容错性解析”掩盖

很多系统之所以越来越难维护，就是因为它们既没有在编译期足够严格，又在运行期试图补锅，最后两边都不清楚责任边界。

## 开源项目在编译链路上的共同取向

虽然 OpenFGA、SpiceDB 在术语和实现上并不完全相同，但它们有一个非常接近的工程直觉：

- 写侧需要 schema/model 这种稳定定义
- 运行侧需要更贴近执行的只读视图
- 解释型字符串不适合直接承担高频授权判断

这也是为什么现代 FGA 系统几乎都会强调：

- 模型版本
- schema 编译
- 可预测的 relation 语义
- 独立于请求对象的 evaluator 内核

这不是“实现偏好”，而是高频权限证明系统的自然演化结果。

## 语法树和图模型分别最容易做错什么

### AST 常见错误

- 解析器和执行器耦合过紧
- 编译器持有请求态
- 节点分类过于粗糙，导致 evaluator 分支膨胀

### 图模型常见错误

- 把图模型理解成必须使用图数据库
- 把运行时搜索直接下推到存储层拼超复杂 SQL
- 混淆 direct tuple 和 propagated relation

## 对开发者最有用的工程判断

如果你在设计自己的 ReBAC 系统，可以记住一句非常实用的话：

**不要让执行器直接解释 DSL，也不要让 DSL 直接等于运行时真相。**

更好的路线是：

- DSL 负责表达
- 结构化模型负责管理
- AST 负责执行语义
- 图模型负责运行时传播视角

这条边界一旦清晰，后面的 evaluator、缓存和 Explain 才容易设计。

## 本文小结

你可以带走五个判断：

1. **DSL 是表达层，不是最终执行层。**
2. **结构化模型是机器可管理的中间真相。**
3. **AST 解决的是关系重写规则的可执行化。**
4. **图模型解决的是运行时传播与证明视角。**
5. **编译链路清晰，才有可能做高性能 evaluator 和稳定缓存。**
