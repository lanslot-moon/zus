# 11. 建模与落地指南：如何把 RBAC、ACL、ABAC 落到 ReBAC 底座

## 为什么很多团队“知道 ReBAC”，却还是做不出来

知道 ReBAC 的概念，不等于知道如何落地。  
落地真正困难的地方，通常不是定义一个 `type document`，而是下面这些问题：

- 现有 RBAC 怎么迁过去
- direct 授权和传播授权如何共存
- 条件到底绑在 model 上还是绑在 tuple 上
- 事实层和业务表如何分工
- `Read` 和 `Check` 的边界怎么讲清楚

这一篇的目标，就是把前面几篇的理论收束成一套实操方法。

## 第一步：先画业务对象，而不是先画权限表

如果你一上来就画：

- role
- permission
- user_role
- role_permission

那你大概率会自动回到 RBAC 的舒适区。  
更好的做法是先问：

- 系统里有哪些真实对象
- 对象之间存在什么结构关系
- 用户与这些对象之间的真实关系是什么

例如：

- organization
- project
- folder
- document
- group
- user

这一步做对了，后面的模型才不会变成空泛 meta-model。

## 第二步：把结构问题和上下文问题分开

一个非常实用的判断标准是：

- **结构问题**：谁属于谁、谁继承谁、谁依赖谁  
  -> 用关系建模
- **上下文问题**：什么时间、什么环境、什么风险等级下成立  
  -> 用条件建模

如果团队做不到这一步分离，模型和条件很快就会混成一团。

## 第三步：先落 direct fact，再落传播规则

ReBAC 建模最稳妥的方式不是一上来就设计复杂传播，而是：

1. 先明确 direct relationship tuple
2. 再定义哪些关系可以传播
3. 最后再加 condition 和 special cases

这样有两个好处：

- 事实层边界更清楚
- 调试和 explain 更容易

## ACL 如何落到 ReBAC 底座

ACL 本质上就是 direct tuple。  
所以落法最简单：

- direct relation
- direct fact

示例：

```fga
model schema 1.1

type user

type document
  relations
    define viewer as this
    define editor as this
```

写入事实：

- `document:doc1#viewer@user:alice`
- `document:doc1#editor@user:bob`

这就是 ACL 在 ReBAC 底座里的自然落点。

## RBAC 如何落到 ReBAC 底座

很多人误以为“用了 ReBAC 就不需要角色了”，这并不对。  
更准确的说法是：**角色需要被放回到关系语义里。**

最常见的做法有两种：

### 方式一：把内建角色定义成 relation

适合：

- 角色稳定
- 角色类型少
- 不需要用户自定义角色

### 方式二：把角色对象化

适合：

- 用户可以定义自定义角色
- 角色是资源局部的
- 角色需要在不同对象上复用

例如：

```fga
model schema 1.1

type user

type role
  relations
    define member as this

type document
  relations
    define owner_role as this
    define editor_role as this
    define viewer_role as this

    define owner as member from owner_role
    define editor as owner or member from editor_role
    define viewer as editor or member from viewer_role
```

这相当于把 RBAC 放回到统一关系图中，而不是让角色系统在外面单跑。

## ABAC 如何落到 ReBAC 底座

这一步最容易做错。

最常见的错误是：

- 试图把所有 ABAC 规则直接写进 model
- 或者直接在接口层临时判断，而不让事实层知道条件存在

更合理的做法通常是：

### 模型层

定义 condition template：

- 名称
- 参数结构
- 表达式

### tuple 层

绑定 condition instance：

- 引用哪个 condition
- 带哪些 context 参数

### request 层

提供运行时 context：

- 当前时间
- IP
- 设备属性
- 风险值

这样就形成了：

- ReBAC 负责路径
- ABAC 负责路径生效条件

## schema 应该如何设计

一套面向现代 FGA 的 schema，至少应考虑下面三层。

### 1. 语义层

- Store
- Authorization Model
- Type Definition
- Relation Definition
- Type Restriction
- Condition Definition

### 2. 事实层

- subject type / id
- object type / id
- relation
- subject relation
- wildcard
- expires
- condition reference
- condition context
- revision/token

### 3. 审计层

- changelog
- operator
- request id
- source
- operation time

如果缺少其中任一层，系统通常都还能跑，但会在：

- 可解释性
- 一致性
- 可维护性

上付出额外代价。

## 写侧和读侧边界必须明确

### 写侧

负责：

- 创建/发布模型
- 写入/删除 tuple
- 写入条件实例
- 记录变更日志

### 读侧

至少要区分：

- `Read`
- `Check`
- `ListObjects`
- `ListUsers`

其中最关键的一句话是：

**`Read` 不是最终授权结果，它只是事实查询。**

因为最终授权结果还要经过：

- 传播
- 条件
- 过期
- consistency

这些语义层的判断。

## 一个落地顺序建议

如果你在重构一个已有系统，可以按下面顺序推进：

1. 抽领域对象和核心关系
2. 先让 direct tuple 跑通
3. 再把传播规则建进 model
4. 再把 `check` 和列表统一进 evaluator
5. 最后再把条件、revision 和 watch 补齐

这样做能把复杂度拆开，不会一开始就把所有问题缠在一起。

## 最终目标不是“写出一份 DSL”

很多团队在做权限重构时，会把“写出一个看起来对的 DSL”当成成功。  
其实 DSL 只是表达层，真正的成功标准应该是：

- direct fact 可表达
- propagated relation 可证明
- `Check / ListObjects / ListUsers` 语义一致
- 条件与 revision 有清晰边界
- 业务团队能读懂模型

如果这些没有做到，再漂亮的 DSL 也只是文本而已。

## 本文小结

把 `ACL / RBAC / ABAC` 落到 ReBAC 底座，本质上不是替换旧系统名词，而是重新整理授权系统的职责分工：

- `ACL` 表达 direct fact
- `RBAC` 表达角色复用
- `ABAC` 表达上下文限制
- `ReBAC` 统一它们的语义与执行

这也是现代细粒度授权系统最有价值的地方：  
不是把所有问题都变复杂，而是把本来已经复杂的问题重新放回一个可理解、可证明、可维护的框架里。
